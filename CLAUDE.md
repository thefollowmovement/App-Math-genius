# App maths enfants — instructions pour Claude Code

App d'exercices de maths (CP → 3e) pour iOS, Android et web, avec comptes parent / enfant, gamification, coach IA et verrou doux.
Le cahier des charges complet est dans `docs/specs.md` : lis la section de la phase en cours avant de coder.

## Skills Expo (obligatoire)

- Pour toute tâche Expo ou EAS, charge d'abord le skill `expo-overview`, puis le skill spécialisé qu'il indique. Ne code jamais de l'Expo de mémoire quand un skill couvre le sujet.
- Si les skills Expo ne sont pas disponibles, arrête-toi et demande d'installer le plugin : `claude plugin install expo@claude-plugins-official`.
- Correspondance avec les phases du cahier des charges :

| Phase | Skills à utiliser |
| --- | --- |
| 0. Socle | `expo-project-structure`, `expo-design-system`, `expo-examples` (Supabase, NativeWind, Skia) |
| 1, 4. Comptes, routine, tableau de bord | `expo-router`, `expo-data-fetching`, `expo-ui` |
| 3, 5, 9b. Séance, gamification, mini-jeux | `expo-animation`, `expo-examples` (Skia) |
| 8. Verrou doux | `expo-module` (Swift FamilyControls + Kotlin), `expo-dev-client` |
| 9c. Mode scroll vidéo | `expo-native-ui` |
| 10. Publication | `eas-app-stores`, `eas-update`, `eas-workflows`, `eas-hosting` |

- Les skills `eas-*` correspondent à des services EAS payants au-delà de l'offre gratuite : demande avant de lancer une commande `eas` qui consomme des crédits (build, submit, update).
- Si un skill Expo est faux ou dépassé, signale-le avec `expo-skill-feedback`.

## Stack

- Monorepo pnpm : `apps/mobile` (Expo, Expo Router, iOS + Android + web), `apps/admin` (back-office Next.js), `packages/curriculum`, `packages/exercise-engine`, `packages/ui`, `packages/shared`, `modules/soft-lock`, `services/ai-gateway`, `supabase/`.
- Expo SDK 57 (React Native 0.86, TypeScript 6), NativeWind v5 (Tailwind v4, d'après l'exemple Expo `with-tailwindcss`), Jest (`jest-expo` pour l'app, `@swc/jest` pour les paquets TypeScript purs).
- TypeScript strict partout, schémas Zod dans `packages/shared`.
- UI : NativeWind + tokens de thème (aucune couleur ni taille en dur dans les écrans), Reanimated, Skia pour les mini-jeux.
- Données : Supabase (Postgres + RLS, Auth, Realtime, Edge Functions, pg_cron), TanStack Query + Zustand côté app.

## Conventions

- Code, noms de fichiers et commentaires en anglais ; textes de l'interface en français, centralisés (pas de chaînes en dur dans les composants).
- Pas de `any`. Composants petits ; logique métier hors des composants.
- `packages/exercise-engine` reste du TypeScript pur, sans React : chaque générateur a des tests (1 000 tirages par difficulté, zéro réponse fausse).
- Le code calcule, l'IA raconte : la bonne réponse vient toujours du moteur, jamais d'un modèle IA.
- Toute nouvelle table Supabase a ses politiques RLS et un test de ces politiques.
- XP, gemmes, séries et validation de séance sont calculés côté serveur.
- Données d'enfants : minimum nécessaire, aucun SDK publicitaire ou analytics tiers dans la partie enfant, rien d'identifiant envoyé à l'IA.

## Thèmes et écrans

- Routes Expo Router dans `apps/mobile/src/app` (uniquement des fichiers de route) ; le corps des écrans va dans `apps/mobile/src/screens`.
- Textes de l'interface dans `apps/mobile/src/i18n/fr.ts`.
- Importer `View`, `Text`, `Pressable` et `ScrollView` depuis `@math-genius/ui` (versions qui acceptent `className`), jamais depuis `react-native` : une règle ESLint l'impose.
- Boutons : `Button` (packages/ui) pose les boutons pleins sur le relief du thème (`relief` : ombre pleine sous le bouton, `border-b-relief`, épaisseur `--theme-relief-depth`, 0 pour un thème plat). Variantes `primary`, `secondary`, `success` (valider une réponse), `accent` (ouvrir une récompense), `outline` (second choix), `ghost`, `danger` ; les pleines brillent d'un halo de leur couleur sur un thème néon. `size="lg"` (64 px) écrit un mot court dans la police des titres (« JOUER ») ; `icon` place un petit dessin avant le titre.
- Halos et reliefs (`global.css`, réglés par `theme.glow` : flou et intensité, 0 sur un thème plat) : `glow-<couleur>` autour d'une vue, `halo-<couleur>` autour d'un texte (pas une classe `text-*`), `ledge` et `ledge-<couleur>` (rebord plein sous une tuile, avec halo pour la sélection). Dégradés : `bg-linear-*`, `from-*`, `to-*` sur les couleurs du thème (natif et web). Une couleur du thème rendue transparente (`bg-primary/15`) reste une couleur du thème. Pas de `blur` (Android seulement) : les lueurs de fond sont des dégradés radiaux SVG (`components/decor.tsx` : `Decor`, `CenterGlow`).
- `Screen` (packages/ui) : `headerless` (page sans en-tête : le contenu commence sous la barre d'état, encoches comprises), `footer` (fixé en bas, hors du défilement, au-dessus de l'indicateur d'accueil : action principale, barre de raccourcis), `top` (fixé en haut : titre et flèches d'une carte), `scrollTo` (position d'ouverture). Les marges de sécurité viennent de `react-native-safe-area-context` (rien hors d'un `SafeAreaProvider`, comme dans les tests). Sans centrage, la colonne remplit la page : une vue `flex-1` repousse ce qui suit vers le bas (le héros au-dessus du bouton).
- Couleurs et rayons uniquement via les classes sémantiques : `bg-background`, `bg-surface`, `bg-raised` (surface plus claire : haut d'une carte mise en avant, bulle), `bg-primary`, `bg-secondary`, `bg-accent` (l'or des récompenses), `bg-success`, `border-border`, `border-primary`, `border-secondary`, `border-accent`, `border-success`, `border-danger`, `border-fire` (série, combo), `text-foreground`, `text-muted`, `text-on-primary`, `text-on-secondary`, `text-on-accent`, `text-on-success`, `text-danger`, `rounded-sm|md|lg|full`. Les textes colorés (étiquettes, scores) passent par les encres du thème (`primaryInk`, `secondaryInk`, `accentInk`, `successInk`, `fire`) : les néons eux-mêmes sur un thème sombre, des teintes plus profondes sur un thème clair, où les couleurs pleines sont des pastels (contraste testé sur le fond et sur les cartes). La palette Tailwind par défaut est supprimée dans `apps/mobile/src/global.css`. Les espacements suivent l'échelle Tailwind (multiples de 4 px).
- Typographie : `ThemedText` avec les variantes `display`, `title`, `score` (chiffres, gros boutons) et `tag` (mot court : nom, compteur) dans la police des titres, `statement` (énoncé d'exercice, grand, dans la police du texte : jamais l'arcade ni la BD pour ce qui se lit de près), `headline`, `body`, `caption` et `label` (petites capitales espacées au-dessus d'une carte). Sa couleur passe par `tone` (`default`, `muted`, `danger`, `onPrimary`, `onSecondary`, `onAccent`, `onSuccess`, et les encres `primary`, `secondary`, `accent`, `success`, `fire`), jamais par une classe `text-*` dans `className` (deux classes de couleur se contrediraient). Les interlignes du `@theme` sont des ratios sans unité (`calc(2.75 / 2.25)`) : en `px` ou `rem`, NativeWind les multiplie par la taille de police sur natif.
- `apps/mobile/src/screens/screens.styles.test.tsx` rend chaque écran avec les styles natifs réels (Tailwind puis le compilateur NativeWind, mêmes options que Metro via `native-css.config.js`) et vérifie espacements et interlignes. Ajoute chaque nouvel écran à sa liste.
- Un thème = un fichier de tokens dans `packages/ui/src/theme/themes/`, enregistré dans `themes/index.ts`. `ThemeProvider` injecte ses valeurs en variables CSS `--theme-*` ; `useTheme()` sert seulement aux API qui n'acceptent pas de classe (barre d'état, navigation, dessins SVG) et `useThemeStrings()` aux textes propres au thème (`strings.themes`). Les tests vérifient le contraste WCAG AA de chaque thème.
- `packages/shared`, `packages/curriculum` et `packages/exercise-engine` n'importent ni React, ni React Native, ni Expo (règle ESLint).
- Ajouter une dépendance à l'app : `pnpm --filter @math-genius/mobile exec expo install <paquet>` pour garder des versions compatibles avec le SDK.
- Écrans purs dans `apps/mobile/src/screens` (données et callbacks en props) ; les routes de `src/app` les branchent sur les hooks de `src/data` (TanStack Query + Supabase). Dans Jest, `@expo/ui` est remplacé par `apps/mobile/jest/expo-ui.tsx`.
- `lightningcss` est figé en 1.30.1 : NativeWind v5 (`react-native-css`) casse sur `var()` avec les versions suivantes. Ne le mets pas à jour sans vérifier `pnpm --filter @math-genius/mobile export`.

## Comptes et base de données

- Le parent se connecte par email et mot de passe ; à l'inscription, un trigger crée sa famille avec le consentement horodaté. L'appareil d'un enfant reçoit une session anonyme Supabase, reliée à un profil par `redeem_pairing_code` ; `revoke_device` lui retire tout accès.
- Les écritures sensibles passent par des fonctions SQL `security definer` qui vérifient l'appelant ; les tables concernées n'ont pas de politique d'écriture.
- Erreurs métier des fonctions SQL : `raise exception '<code>' using errcode = 'PTxyz'` (PostgREST renvoie le statut HTTP xyz). L'app les traduit dans `apps/mobile/src/data/errors.ts` et `strings.errors`.
- Après une migration : `pnpm supabase:reset`, `pnpm supabase:test`, puis `pnpm supabase:types` (la CI vérifie que les types sont à jour).
- Après une écriture qui change le résultat d'une requête peut-être déjà partie (appairage : la requête des profils démarre dès la connexion anonyme), utiliser `refetchAfterWrite` (`data/query-client.ts`) plutôt que `invalidateQueries` seul : une invalidation réutilise une requête en cours qui n'a pas encore de données, même si elle a lu la base avant l'écriture.

## Référentiel et moteur d'exercices

- `packages/curriculum` : compétences de la CE2 à la 5e, par niveau (`src/grades/`), chacune avec son domaine du test de positionnement (`strand`, phase 7). Les codes `<niveau>.<slug>` sont stables (la maîtrise de chaque enfant y est rattachée) : ne jamais les renommer. Prérequis du même niveau ou d'un niveau inférieur, sans cycle (testé). Le contenu est un brouillon à faire relire par un enseignant.
- Ajouter un générateur : un fichier dans `packages/exercise-engine/src/generators/<niveau>/`, de moins de 30 lignes non vides (vérifié par un test), qui importe tout depuis `../kit`, puis une ligne dans `generators/index.ts`. Les tests de 1 000 tirages par difficulté s'appliquent alors automatiquement.
- Réponses en nombres exacts (`r()`, `decimal()`), jamais de flottants ; nombres affichés au format français avec `n()`, `frac()`, `op()`.
- Chaque exercice porte un `check` : le calcul ou l'énoncé derrière la réponse, écrit avec les nombres de l'énoncé. L'oracle des tests (`src/testing/oracle.ts`, en BigInt, sans code commun avec le moteur) le recalcule et vérifie que chaque nombre du `check` apparaît bien dans l'énoncé. Pour une nouvelle notion (formule, unité), ajouter sa fonction à l'oracle avec un test, pas au moteur.
- Le correcteur (`gradeResponse`) accepte toutes les écritures d'une même valeur (0,5 = 0.5 = 1/2), sauf si l'exercice impose `forms` ou `irreducible` ; il distingue une valeur juste mal écrite (`wrong-form`, `not-irreducible`) d'une erreur.

## Séance, adaptatif et hors-ligne

- Moteur adaptatif dans `packages/exercise-engine/src/adaptive/` : notes Elo enfant × item (`ratings.ts`), maîtrise 0-100, oubli et statuts (`mastery.ts`), règles de séance (`session.ts`) et planificateur (`planner.ts`). L'exercice suivant est une fonction pure du contexte de départ et des réponses déjà données : une séance interrompue reprend à l'identique. Composition 40 / 30 / 20 / 10 (`SLOT_PATTERN`), exercice jumeau 3 exercices après une erreur, rappel et difficulté abaissée après 2 erreurs d'affilée. `src/testing/learner.ts` simule des élèves virtuels (taux de réussite visé 75-85 %).
- La fonction SQL `sync_session` recalcule côté serveur le score, le temps actif, la validation (objectif atteint avec au moins 60 % de réussite) et le signalement des réponses trop rapides, avec les mêmes constantes que `session.ts` et `ratings.ts`. Changer une règle, c'est changer les deux : le test de `session.test.ts` et `practice_sessions.test.sql` partagent le même cas, et `sync-contract.test.ts` compare les champs envoyés par l'app aux colonnes lues par la migration.
- Côté app, tout passe par `apps/mobile/src/data/practice/` : `practice-store.ts` (Zustand persisté dans AsyncStorage : maîtrise, séance en cours, sessions à envoyer), `sync-engine.ts` (payload et envoi, sans Supabase, testable) et `sync.ts` (branchement Supabase, envoi au retour du réseau et au retour au premier plan). Chaque réponse est enregistrée sur l'appareil dès qu'elle est donnée ; l'envoi renvoie toute la séance et ne crée jamais de doublon. Les profils (cache TanStack Query) sont gardés une semaine sur l'appareil, NetInfo pilote `onlineManager`, et une session Supabase expirée reste utilisable hors-ligne (`data/session.ts`).
- Les écrans d'exercice sont dans `apps/mobile/src/screens/practice/` (une saisie par type dans `inputs/`, clavier intégré, jamais le clavier système). La logique de séance est dans `hooks/use-practice-session.ts`.
- La table `skills` est remplie par des migrations générées depuis `packages/curriculum` : après un changement du référentiel, lancer `pnpm curriculum:sql` (un test échoue sinon). Appliquer les migrations avant de publier une version de l'app qui utilise de nouvelles compétences.
- Tests de l'app : `jest/setup.ts` simule AsyncStorage, NetInfo et Gesture Handler ; Reanimated tourne grâce au resolver de `react-native-worklets`. Les imports CSS sont remplacés par `jest/css-stub.js`, et `renderRouter` (`expo-router/testing-library`) rend de vraies routes. `fetch` est simulé par `jest-expo` : les tests ne joignent jamais Supabase, d'où le transport injectable de `sync-engine.ts`.

## Suivi parent (phase 4)

- Séances du jour côté parent : `apps/mobile/src/data/family-sessions.ts` (requêtes et abonnement Realtime) et `data/session-report.ts` (état du jour par enfant, état d'une séance, lecture des réponses stockées). La table `sessions` est publiée dans Supabase Realtime (migration `*_parent_live_sessions.sql`) ; Realtime applique ses politiques RLS, donc un parent ne reçoit que les séances de ses enfants. Un seul abonnement, ouvert dans `app/parent/_layout.tsx`, rafraîchit toutes les pages parent ; il recharge aussi les séances dès qu'il est actif, pour ne rien manquer de ce qui précède.
- Le texte des exercices n'est jamais stocké : le détail d'une séance les reconstruit avec le moteur (générateur, difficulté, graine). Un générateur retiré d'une version de l'app s'affiche comme « exercice indisponible ».
- Routines et vacances : tables `routines` (une par enfant : jours ISO 1 = lundi … 7 = dimanche, début, début du mercredi et du week-end, heure limite, objectif) et `vacations` (premier et dernier jour inclus, 92 jours au plus). Le parent les écrit directement (RLS) ; l'appareil de l'enfant les lit. Les règles du jour (prévu, repos, vacances) sont dans `packages/shared/src/routine.ts` (`dayPlan`) et, côté serveur, dans `private.day_plan` : changer l'une, c'est changer l'autre (`routine.test.ts` et `routines.test.sql` partagent le même cas).
- Statut du jour (`childDay`) : une séance terminée (pas un test de positionnement) fait « terminé », même en retard ; passé l'heure limite d'un jour prévu, rien de terminé fait « manqué » ; un jour de repos ou de vacances sans séance n'est pas manqué. Le tableau de bord recalcule ce statut chaque minute (`hooks/use-local-clock.ts`), sans recharger.
- Une nouvelle séance prend l'objectif de la routine (`use-start-session.ts`), 15 minutes sans routine ; la routine est gardée sur l'appareil (cache TanStack Query persisté) pour démarrer hors-ligne. Une séance en cours garde l'objectif de son début. Les fonctions pures sont dans `data/routine-plan.ts`, les requêtes Supabase dans `data/routines.ts`.
- Heures et dates se choisissent avec le `Picker` d'@expo/ui (créneaux de 15 minutes) : le `DateTimePicker` d'@expo/ui n'affiche rien sur le web.
- Rappels côté serveur (migration `*_reminders.sql`) : pg_cron lance `private.run_reminders()` chaque minute. `private.enqueue_reminders(p_now)` met en file les étapes dues, à l'heure de la famille (`families.timezone`) : H − 10, H et H + 30 pour l'enfant, H + 60 et l'heure limite pour le parent, plus la fin de la séance du jour. Une étape part dans les 10 minutes qui suivent son heure, sinon elle est sautée (jamais de rappel en retard) ; rien un jour de repos, en vacances ou après une séance terminée (un test de positionnement ne compte pas), et pas de rappel à l'enfant pendant qu'il joue (réponse envoyée depuis moins de 10 minutes). `notifications.dedup_key` empêche tout doublon. Les tests pgTAP passent `p_now` pour simuler l'horloge.
- Envoi : `private.send_notifications` poste à l'API Expo Push avec pg_net (aucune Edge Function, aucune clé : l'API Expo Push n'en demande pas tant que la sécurité renforcée des push n'est pas activée sur le projet Expo). `private.collect_push_receipts` lit les réponses à la minute suivante et supprime le jeton d'un appareil désinstallé (`DeviceNotRegistered`). Les notifications sont gardées 30 jours.
- Les textes des notifications sont écrits en SQL (`private.notification_content`) : le téléphone les affiche lui-même, app fermée. C'est la seule exception à `fr.ts`.
- Jetons push : `register_push_token` (au démarrage, parent et appareil enfant, une fois les notifications autorisées), `unregister_push_token` (à la déconnexion). Code de l'app : `lib/notifications.ts` (permission, jeton, ouverture de l'écran au toucher, limitée aux routes `/child/` et `/parent/`) et `data/push.ts`. Sans `expo.extra.eas.projectId` dans `app.json` (écrit par `eas init`), l'app ne demande pas de jeton. Le web n'en a pas.
- `expo-notifications` est optionnel : ne jamais l'importer en tête de fichier (seulement `import type`), toujours passer par `loadNotifications()`. Sur Android, Expo Go n'a plus ses modules natifs depuis le SDK 53 : charger le paquet y lève une erreur qui faisait planter toutes les routes. `loadNotifications()` ne le charge jamais sur web ni dans Expo Go sur Android, et le charge ailleurs dans un `try`. `src/app-start.test.tsx` démarre le vrai layout racine avec un module absent.
- Chaque appareil enfant signale s'il peut afficher les notifications (`report_push_status` : `enabled`, `denied` ou `unsupported`, colonne `devices.push_status`). La fiche de l'enfant l'affiche pour chaque appareil, et le panneau de message avertit le parent quand aucun appareil ne peut les recevoir.
- Message du parent : `send_child_message` (120 caractères, un toutes les 2 minutes par enfant, envoyé tout de suite) renvoie le nombre d'appareils joints ; 0 veut dire qu'aucun appareil de l'enfant n'a autorisé les notifications.

## Récompenses (phase 5)

- Recorrection serveur : l'XP et les gemmes ne viennent jamais de ce que l'appareil a jugé. Après chaque envoi d'une séance terminée (`sync.ts`), l'app appelle l'Edge Function `award-session` (`supabase/functions/award-session/index.ts`). Elle lit les séances à récompenser avec le jeton de l'appelant (RLS), reconstruit chaque exercice avec le moteur (`regrade` de `packages/exercise-engine/src/regrade.ts`), note à nouveau chaque réponse stockée et passe ses verdicts à `award_session`, réservée à `service_role`. `award_session` est idempotente : un nouvel appel renvoie la récompense déjà donnée (`sessions.award`).
- Le moteur est embarqué dans les fonctions sous forme d'un bundle généré, `supabase/functions/_shared/engine.js` (esbuild, sans import, depuis `packages/exercise-engine/src/server.ts`), partagé par `award-session` et `learner-profiles`. Après un changement du moteur, du référentiel ou de `packages/shared`, lancer `pnpm functions:bundle` (un test échoue sinon), puis redéployer les deux fonctions sur le projet en ligne. `packages/shared` est déclaré `sideEffects: false` et `grade.ts` n'importe pas Zod (`grade-schema.ts` à part) : sans cela, Zod entrerait dans le bundle.
- La fonction ne s'appuie pas sur la vérification JWT de la passerelle (`verify_jwt = false` dans `config.toml`) : PostgREST et la RLS vérifient le jeton et la clé de l'appelant, qu'elle transmet tels quels. Sans jeton, elle répond 401.
- Règles dans `packages/shared/src/rewards.ts` et dans la migration `*_rewards.sql` : changer l'une, c'est changer l'autre (`rewards.test.ts` et `rewards.test.sql` partagent le même cas). 10 XP par bonne réponse vérifiée, sauf en moins de 1,2 s ; +10 XP par série de 5 bonnes réponses d'affilée ; le niveau L demande 50 × L × (L − 1) XP. La séance du jour validée (objectif atteint et 60 % de bonnes réponses vérifiées) rapporte 5 gemmes et un coffre (5 à 15 gemmes, rare tous les 7 jours de série : 25 à 50), tirés d'un hachage de la séance.
- Série : rejouée sur tout l'historique (`private.streak_state`), donc une séance envoyée en retard compte pour son jour. Les jours de repos et de vacances sont ignorés, aujourd'hui n'est jamais manqué, et un jour manqué consomme un gel s'il en reste. Un gel gratuit chaque lundi ; un gel acheté coûte 30 gemmes (`buy_freeze`), 3 au plus. pg_cron recalcule la progression chaque heure (`refresh-progress`) ; une ligne de `progress` inchangée n'est pas réécrite.
- Tables `progress`, `gem_transactions` (le solde de gemmes est leur somme) et `chests` : lecture seule pour la famille (RLS), écritures par `award_session`, `open_chest` et `buy_freeze`. `progress` est publiée dans Realtime : la fiche de l'enfant côté parent suit série, niveau et gemmes en direct (même abonnement que les séances).
- Badges : catalogue dans `packages/shared/src/badges.ts` (code, famille, mesure, seuil) et dans les migrations (`*_badges.sql`, puis `*_islands.sql`, `*_challenges.sql` et `*_companions.sql` ; `badges.test.ts` compare le tout) ; icônes, titres et descriptions dans `fr.ts` (`strings.badges.items`, typé par code). Les codes sont stables : ne jamais les renommer. `private.badge_metrics` calcule les mesures uniquement à partir des données du serveur (réponses recorrigées, série, coffres, gemmes, maîtrise) ; `award_session` accorde les badges atteints et renvoie les nouveaux dans la récompense (`badges`). Ajouter un badge : une ligne dans `badges.ts`, la même dans une nouvelle migration, et ses textes ; une nouvelle mesure : une clé de `BADGE_METRICS` et de `private.badge_metrics`. Ce qu'une séance rapporte en plus de l'XP et des gemmes passe par `private.award_extras` (défi, boss, récompenses du parent, puis badges) : le compléter plutôt que réécrire `award_session`. `private.badge_metrics` est chaînée de migration en migration (renommée, puis complétée).
- Carte du monde (`packages/exercise-engine/src/adaptive/islands.ts`, pur) : une île par domaine de la classe de l'enfant, le chemin de ses compétences (statut de maîtrise, « pas encore ouverte » tant qu'un prérequis manque, « bientôt » sans générateur) et un boss. Le boss s'ouvre quand toutes les compétences de l'île qui ont des exercices ont été maîtrisées une fois. Une séance de boss (`kind: 'boss'`, île gardée dans la séance) passe par `planNext` (`context.boss` → `planBossExercise`) : chaque compétence de l'île à tour de rôle, 2 par compétence entre 6 et 10 exercices (`bossLength`), sans jumeau ni rappel. Le serveur retrouve l'île à partir des compétences jouées (`private.settle_boss`, migration `*_islands.sql`) ; 80 % de bonnes réponses recorrigées sur au moins 6 exercices (`BOSS_PASS_RATE`, `BOSS_MIN_EXERCISES` dans `rewards.ts`) terminent l'île (`island_completions`), et la récompense le dit (`boss`). Une séance de boss rapporte de l'XP, ni gemmes du jour, ni coffre, ni jour de série. Écran `screens/world-map/`, route `child/map`.
- Boutique (migration `*_shop.sql`, catalogue réécrit en entier par `*_companions.sql` puis `*_outfits.sql`) : catalogue dans `packages/shared/src/shop.ts` et dans la dernière migration qui l'écrit (`shop.test.ts` compare les deux), noms et icônes dans `fr.ts` (`strings.shop.items` ; les compagnons dans `strings.companions`, les tenues dans `strings.outfits`). ## Test de positionnement (phase 7)

- Domaines du test : chaque compétence a un `strand` (`numeration`, `calcul`, `fractions`, `mesures`, `geometrie`, `problemes` : `STRANDS` dans `packages/curriculum`), plus fin que les domaines des îles. L'algèbre va avec le calcul, les données, la proportionnalité et les probabilités avec les problèmes. TypeScript l'impose à toute nouvelle compétence.
- Moteur (`packages/exercise-engine/src/adaptive/placement.ts`, pur) : par domaine, une échelle de paliers, un par classe qui a des exercices, jusqu'à la classe au-dessus (`placementRungs`). Difficulté 3 sous la classe, 2 sur la classe (les bases de l'année), 3 au-dessus. Pour un CE2, un palier en plus, fait des exercices de CE2 les plus faciles, tient lieu de CE1 (le référentiel commence au CE2). Le test part de la classe de l'enfant, monte après un palier réussi, descend après un palier raté, jusqu'à encadrer le niveau. Un palier se décide sur 2 réponses concordantes, sinon une 3e : une étourderie ne fait pas changer de classe. Les domaines jouent à tour de rôle, 25 questions au plus (`PLACEMENT_MAX_QUESTIONS`) ; moins quand le référentiel n'a plus de niveau au-dessus (une 5e forte : une dizaine). Une séance de test (`kind: 'placement'`, `context.placement`) passe par `planNext` → `planPlacementExercise`, fonction pure des réponses : un test interrompu reprend à l'identique.
- Résultat (`placementResult`) : par domaine, le palier le plus haut réussi. « En avance » au-dessus de la classe ; « au niveau » sur la classe ou sur celle d'avant (en début d'année, le programme de l'année est encore enseigné) ; « à consolider » en dessous ; `null` sans exercice (géométrie). Trois priorités : les compétences ratées, les plus fondamentales d'abord et de domaines différents, puis les prochaines à apprendre.
- Pré-remplissage (`placementMastery`, que `finishSession` appelle à la fin du test) : chaque compétence que l'enfant peut travailler reçoit un enregistrement. Sa note vient du palier atteint (`PLACED_ELO` : acquise jusqu'au palier réussi, puis une classe à la fois), les réponses du test par-dessus ; une compétence déjà travaillée garde sa note. Sont acquises (`masteredAt`) celles des classes d'avant sous le palier réussi, et les prérequis d'une classe d'avant d'une compétence réussie plus haut ; jamais une compétence ratée, et pas d'office celles de l'année, que la pratique confirme. Une compétence acquise par le test est maîtrisée sans pratique (`masteryStatus`, carte du monde).
- Après le test, l'enfant est « placé » (`PlannerContext.placed`, `worldMap({ placed })`) : les classes d'avant ne sont plus présumées connues, ses enregistrements disent ce qui l'est (`isAcquired`), donc les lacunes passent en premier. `simulatePlacement` (`src/testing/learner.ts`) joue un test ; le critère de validation (« résultat cohérent pour 3 profils d'élèves simulés ») est dans `placement.test.ts`.
- Recalage (`placementDue`) : jamais passé, passé il y a plus de 3 mois, ou avant le 1er septembre de l'année scolaire. C'est le même test, présenté comme un « Point d'étape ».
- Base (migration `*_placement.sql`) : chaque séance garde la classe de l'enfant au moment où elle est jouée (`sessions.grade`, trigger), pour relire un test même après un changement de classe. Le test rapporte de l'XP, ni gemmes, ni coffre, ni jour de série. Ce n'est pas la séance du jour : il n'arrête pas les rappels (`private.enqueue_reminders`, remplacée) et ne compte pas dans le statut du jour (`childDay`). « Je ne sais pas » est stocké `{ type: 'skipped' }` (`SKIPPED_ANSWER`, `isSkippedAnswer`) : faux pour l'appareil et pour la recorrection serveur. L'avertissement des réponses trop rapides ne s'affiche pas pour un test (`showsFastAnswers`) : un « Je ne sais pas » rapide est une réponse honnête.
- App, enfant : `practice-store.ts` (`openSession({ placement: true })` ; `placedAt` gardé sur l'appareil et relu sur le serveur par `sync.ts`, `mergePlacedAt`) ; `sync-engine.ts` (un test terminé envoie tous les enregistrements qu'il conclut) ; `data/placement-model.ts` (`placementOffer` : premier test, recalage ou test en cours sur l'accueil) ; `hooks/use-placement-session.ts` (ni correction ni score : une réponse mène à la question suivante). Écrans `screens/placement/` : intro « Aventure de départ » (route `child/placement`, juste après l'intro du héros pour un nouvel enfant), questions (« Je ne sais pas », ni chrono ni compteur), révélation de la carte et première mission (route `child/placement-result`) ; carte sur l'accueil (`child-home/placement-card.tsx`). Un test ou un boss demandé prend la place d'une séance ouverte sans réponse.
- App, parent : `data/placement.ts` (dernier test et ses réponses, sous la clé `sessions` : l'abonnement temps réel le rafraîchit) et `data/placement-report.ts` (le moteur relit les réponses, verdict du serveur d'abord) ; panneau `screens/child-detail/placement-panel.tsx` : date et classe du test, niveau par domaine, 3 priorités.

## Profil et univers (phase 7b)

- Erreurs typiques : catalogue `ERROR_TYPES` dans `packages/curriculum/src/error-types.ts` (code stable, jamais renommé ; libellé à la 3e personne, « oublie la retenue » ; compétences concernées), chargé dans la table `error_types` par la migration `*_skills.sql` générée (`pnpm curriculum:sql`). Chaque générateur donne, dans le champ `mistakes` de l'exercice, les réponses qui trahissent une erreur typique, calculées avec les nombres de l'énoncé et sans tirage aléatoire en plus (un même `seed` donne toujours le même exercice). Le test des 30 lignes ne compte pas les blocs `mistakes`. `diagnoseResponse` (`diagnose.ts`) nomme l'erreur d'une réponse fausse ; `regrade` la renvoie (`error`) et `award-session` la range dans `attempts.error_type` (`record_answer_errors`, réservée au serveur). Ajouter une erreur : une ligne dans `ERROR_TYPES`, la réponse dans le générateur, puis `pnpm curriculum:sql` et `pnpm functions:bundle` (`diagnose.test.ts` vérifie que chaque erreur est diagnostiquée et atteinte).
- Profil d'apprentissage (`packages/exercise-engine/src/adaptive/profile.ts`, pur) : à partir des 30 derniers jours (et du dernier test de positionnement de la classe), des forces (en avance, à l'aise sur 2 compétences de l'année, calcul mental rapide, longue série de bonnes réponses ; à défaut, le meilleur domaine du moment), des points à travailler (erreurs typiques répétées, domaine à consolider, compétences qui redescendent ou qui bloquent) et une façon d'apprendre (attention au fil de la séance, moment de la journée, réaction après une erreur, réussite des jumeaux). Attention et moment de la journée comparent la réussite à ce que la note de l'enfant prévoit : la difficulté adaptative ne les masque pas. Après des semaines de pratique, un « en avance » du test n'est gardé que si la pratique ne le contredit pas. `profileSummary` (`profile-summary.ts`) écrit le résumé compact envoyé au futur coach : en français, sans prénom ni rien d'identifiant, sans mot accordé au genre ; c'est une exception à `fr.ts`, comme les notifications. `testing/child.ts` simule des enfants avec leurs habitudes ; le critère de la phase (3 profils simulés cohérents, rien d'inventé pour un enfant sans habitude) est dans `profile.test.ts`.
- Consentement : à part, par enfant (`children.personalization_consent_at` et sa version, `PERSONALIZATION_CONSENT_VERSION` dans `packages/shared/src/personalization.ts`), donné par le parent seul (`set_personalization`). Sans lui, rien n'est demandé, calculé ni gardé : le retirer (fonction ou mise à jour directe de l'enfant, trigger `private.clear_personalization`) supprime centres d'intérêt, réponses libres et profil.
- Univers (migrations `*_personalization.sql` et `*_universes.sql`) : `universes` (nom, catégorie, classes autorisées selon l'âge et le PEGI, mots et images pour le coach, date de revue), `interest_questions` (les 6 questions, réponse libre « Autre » au collège) et `interest_options` (icône neutre, jamais un logo) ; lecture pour tous, écriture par le futur back-office. Fortnite (PEGI 12) à partir de la 5e, aucun jeu PEGI 16 ou 18, personnes réelles à partir du CM1. Les réponses (`child_interests`, `source` questionnaire ou parent) passent par `set_child_interests` (appareil de l'enfant ou parent, choix vérifiés pour la classe ; une réponse remplace la précédente pour la même question) ; les réponses libres (`interest_other_answers`) attendent la modération. `skip_universe` (« Plus tard ») et une réponse de l'enfant datent le questionnaire (`universe_asked_at`) : il revient au bout de 3 mois et à chaque rentrée (`universeDue`).
- Calcul côté serveur : `profile_input` rassemble pour un enfant (avec consentement) séances, réponses, erreurs, maîtrise, notes des items et noms des univers ; `save_learner_profile` range profil et résumé (`learner_profiles`, lecture par la famille) ; tout est réservé à `service_role`. `award-session` recalcule le profil après chaque récompense ; pg_cron appelle chaque heure `private.request_profile_refresh`, qui poste avec pg_net vers l'Edge Function `learner-profiles` (100 profils dus par appel : plus de 20 heures, ou réponses à l'univers changées depuis, `children.interests_updated_at`). L'adresse et la clé viennent de Vault (`project_url`, `service_role_key`) : `pnpm supabase:cron-secrets` les écrit en local (à relancer après `pnpm supabase:reset`) ; sans elles, rien ne part. Code partagé des fonctions : `supabase/functions/_shared/profiles.ts` et `profileFromInput` (`src/server.ts`, testé contre le calcul direct).
- App, enfant : questionnaire « Ton univers » (`screens/universe/`, route `child/universe`, paramètres `mode=edit` et `then` : `play`, `map`, `back` ou `home`) : mot du héros, une question par écran (cartes à toucher, deux par ligne), « Autre » au collège, puis « C'est noté ! ». Il suit le résultat du test de positionnement (`placement-result.tsx`), revient en carte sur l'accueil quand il est dû (`child-home/universe-card.tsx`, pas avant le premier test) et se modifie depuis « Mon héros » (`look/universe-section.tsx`). Le « super-pouvoir » (`child-home/super-power-card.tsx`) est la première force du profil (`superPower`, `data/learner-profile-model.ts`, qui relit le profil en laissant de côté ce qu'il ne connaît pas). Données : `data/universe.ts` (catalogue, réponses, profil, consentement ; gardés sur l'appareil) et `data/universe-model.ts` (pur). Les questions et les noms des univers viennent de la base (contenu du back-office), le reste des textes de `strings.universe` et `strings.superPower`.
- App, parent : panneau `screens/child-detail/profile-panel.tsx` (hook `use-profile-panel.ts`) : avant l'accord, ce que fait la personnalisation ; ensuite les forces d'abord, les points à travailler, la façon d'apprendre (`i18n/profile-text.ts`), l'univers et les réponses libres avec leur statut, « Modifier son univers » (route `parent/children/[id]/universe`, le même questionnaire) et « Désactiver la personnalisation » après confirmation.

## Coach IA et back-office (phase 7c)

- Explications à trous (`packages/exercise-engine/src/coach/`) : l'IA n'écrit jamais un nombre, elle utilise les repères de l'exercice (`coachFrame` : `{n1}`… pour l'énoncé, `{e1}`… pour la correction, `{reponse}`, `{solution}`). `renderExplanation` met les nombres à leur place et `showableExplanation` vérifie le résultat : ni chiffres ni nombres en lettres dans le modèle, aucun nombre étranger à l'exercice et à sa correction (`foreignNumbers`), moins de 60 mots, aucun repère inconnu. Le test de propriété de `coach.test.ts` le vérifie sur tous les générateurs. Format : `{ what, image, tip }` (ce qui s'est passé, l'image, l'astuce). `coachSample(skill, error)` trouve un exercice qui montre une erreur (nuit, test de prompt, relecture).
- Cache : une explication sert à tous les enfants de la même combinaison compétence × erreur typique × univers (ou vie quotidienne) × tranche d'âge (`GRADE_BANDS`, `gradeBand` dans `packages/shared` ; `private.grade_band` côté base). Tables (migrations `*_ai_coach.sql` puis `*_coach_night_runs.sql`) : `explanations` (`pending` à la création, `approved` ou `rejected` par un modérateur, une rejetée n'est plus jamais montrée), `explanation_feedback` (« J'ai compris », « Explique autrement »), `ai_usage` (chaque appel : coût, latence, résultat, problèmes ; l'enfant seulement pour les coûts), `ai_settings` (une ligne : interrupteur d'urgence, fournisseurs temps réel et nuit, modération, plafonds du jour et du mois, lot de nuit), `ai_prompts` (versions, une active par tranche), `ai_banned_words`.
- `services/ai-gateway` (TypeScript pur, testé) : fournisseurs (API Mistral ou serveur compatible OpenAI : Ollama, llama.cpp, vLLM ; `providers.ts`), prompt (`prompt.ts` ; `DEFAULT_PROMPT` est la version 1 de la migration, `prompt.test.ts` compare), lecture et contrôles (`checks.ts` : JSON, contrôles du moteur, mots interdits, puis modèle de modération de Mistral), `explain` (bonne réponse ou interrupteur coupé : rien, cache compris ; puis cache, budget, génération, gardée en `pending`), `pregenerate` (nuit), `preview` (test du back-office) et lecture de la base (`context.ts`). Bundle généré `supabase/functions/_shared/ai-gateway.js` (`pnpm functions:bundle`, un test échoue sinon).
- Edge Function `ai-gateway` (`verify_jwt = false`, elle vérifie chaque appelant) : `explain` (jeton de l'appareil ou du parent, la RLS dit s'il voit l'enfant ; l'exercice est reconstruit depuis générateur, difficulté et graine ; réponse `{ source: 'cache' | 'ai', id, template, explanation }` ou `{ source: 'standard', reason }`), `night` (clé service seulement), `preview` (éditeur ou super-admin, `admin_whoami`). Les clés d'API sont des secrets des Edge Functions (`MISTRAL_API_KEY`, `OWN_AI_API_KEY`), jamais dans la base. Fonctions SQL réservées à `service_role` : `coach_context`, `coach_cached`, `coach_save_explanation`, `coach_shown`, `coach_log_usage`, `coach_night_plan`, `coach_preview_context`. Sans clé Mistral ni serveur perso, le coach répond « standard ». En local, un serveur sur la machine se joint depuis les conteneurs à `http://host.docker.internal:<port>`.
- Nuit : pg_cron appelle `private.request_coach_night()` toutes les 15 minutes de 1 h à 4 h 45 UTC (une Edge Function s'arrête après 150 s : aucun appel ne commence après 90 s). `night_batch` est le total d'une nuit ; chaque passage reçoit ce qui reste (`private.coach_night_left`) et laisse de côté ce qui a été essayé cette nuit. Priorité (`nightJobs`) : les erreurs les plus fréquentes des 30 derniers jours par tranche, la vie quotidienne d'abord, puis les univers les plus choisis. Le serveur perso s'il est réglé, le modèle temps réel sinon. Mêmes secrets Vault que les profils.
- App : après une erreur, `hooks/use-coach.ts` appelle la fonction (`data/coach.ts`). Le texte rendu par le serveur n'est jamais affiché : `data/coach-model.ts` rend le modèle avec les nombres de l'exercice et le revérifie avec le moteur. Le héros réfléchit pendant la recherche, puis présente l'explication dans sa bulle (`screens/practice/coach-bubble.tsx`, depuis `hero-line.tsx`), sous la correction du générateur, toujours affichée. « J'ai compris » est noté (`coach_feedback`) et continue ; « Explique autrement » demande une autre explication (celles déjà vues exclues, un autre univers) et garde la dernière quand il n'y en a plus. Hors-ligne, IA coupée, erreur ou rien de montrable : la correction seule. Les explications ne sont pas gardées sur l'appareil. Textes : `strings.practice.coach`.
- Back-office (`apps/admin`, Next.js 16, App Router, Tailwind v4 avec les jetons sémantiques de `src/app/globals.css`, palette par défaut supprimée) : des pages client avec la clé publishable ; chaque lecture et écriture passe par la RLS et les fonctions `admin_*`, qui revérifient le rôle. Textes dans `src/i18n/fr.ts`, logique pure dans `src/models/` (testée), requêtes dans `src/data/` (TanStack Query). Rôles (`admin_users`, `private.is_admin`) : super-admin (tout), éditeur pédagogique (tendances, questionnaire, prompts, coûts, relecture), modérateur (radar et réponses « Autre », relecture) ; le menu suit `models/navigation.ts`. Chaque modification d'une table gérée par l'équipe est tracée par `private.audit_admin_change` dans `admin_audit_log` (qui, quand, avant, après). Les comptes de l'équipe n'ont pas de famille (pas de métadonnées de parent).
- Pages : Tendances et univers (catalogue, revue tous les 3 mois avec alerte, activation ou retrait en un clic, formulaire pré-rempli depuis une réponse « Autre » ; la règle d'âge est dans la base, contrainte `universes_pegi_grades` : jamais PEGI 16 ou 18, PEGI 12 de la 5e à la 3e), Radar (carte de chaleur des choix par mois et tranche, réponses « Autre » regroupées, validées, rejetées ou ajoutées au catalogue), Questionnaire (titres, posée ou non, ordre, choix et icônes), IA : modèles et budget (interrupteur d'urgence, fournisseurs, modération, plafonds, lot de nuit, coûts par jour et par enfant pseudonyme ; seul le super-admin modifie), IA : prompts (versions, activation, nouvelle version, test en direct), IA : relecture (file, chaque explication sur un exemple du moteur, taux de compréhension, mots interdits, journal de modération `admin_moderation_log`), Journal et Équipe (super-admin). L'app lit le catalogue et le questionnaire dans la base : une tendance ajoutée et proposée apparaît sans mise à jour.
- Ajouter une page : son id et ses rôles dans `models/navigation.ts`, sa route dans `src/app/(admin)/`, son titre dans `strings.pages`.

## Façon de travailler

- Une phase = une branche. Ne code rien au-delà de la phase demandée.
- Termine chaque phase en listant ce qui manque par rapport à son critère de validation dans `docs/specs.md`.
- Mets à jour la section Commandes ci-dessous dès qu'une commande est ajoutée.

## Commandes

Prérequis : Node 22 (`.nvmrc`), pnpm 10 (`corepack enable`), Docker Desktop installé et lancé pour Supabase local.

Sur un téléphone (Expo Go), `127.0.0.1` désigne le téléphone lui-même. En développement, l'app remplace donc l'hôte d'une URL Supabase locale par l'adresse IP du Mac sur le réseau, déduite de l'hôte Metro (`Constants.expoConfig.hostUri`, voir `apps/mobile/src/lib/dev-host.ts`) : rien à modifier dans `.env.local`. Il faut que le téléphone et le Mac soient sur le même Wi-Fi, que Docker Desktop tourne avec `pnpm supabase:start` (l'API écoute sur toutes les interfaces, port 54321) et, si le pare-feu de macOS est actif, qu'il accepte les connexions entrantes vers Docker. En mode tunnel (`--tunnel`), seul Metro passe : Supabase local n'est alors pas joignable.

**Supabase en ligne** (tests sur de vrais téléphones sans Mac allumé, ou hors du Wi-Fi local). Créer un projet sur supabase.com (région Europe), puis depuis la racine du dépôt :

1. `pnpm exec supabase login`, puis `pnpm exec supabase link --project-ref <ref>` (le `ref` est dans l'URL du projet ; le mot de passe demandé est celui de la base).
2. `pnpm exec supabase db push` : applique toutes les migrations de `supabase/migrations`, y compris les `*_skills.sql` générées depuis le référentiel. À relancer après chaque nouvelle migration. `seed.sql` n'est pas envoyé. Puis `pnpm exec supabase functions deploy award-session`, `pnpm exec supabase functions deploy learner-profiles` et `pnpm exec supabase functions deploy ai-gateway` : déploient la recorrection serveur qui donne XP, gemmes et coffres, le calcul des profils d'apprentissage et le coach IA (à relancer après chaque `pnpm functions:bundle`). Le coach a besoin d'une clé : `pnpm exec supabase secrets set MISTRAL_API_KEY=<clé>` (console.mistral.ai), ou d'un serveur perso réglé dans le back-office (`OWN_AI_API_KEY` s'il demande une clé). Pour le calcul des profils et la pré-génération des explications chaque nuit, exécuter une fois dans le SQL Editor du tableau de bord `select vault.create_secret('https://<ref>.supabase.co', 'project_url');` puis `select vault.create_secret('<clé service_role>', 'service_role_key');` (Project Settings → API Keys, onglet des clés héritées) : sans ces deux secrets, la tâche horaire ne fait rien (les profils restent recalculés après chaque séance). Elle utilise les variables `SUPABASE_URL`, `SUPABASE_ANON_KEY` et `SUPABASE_SERVICE_ROLE_KEY`, fournies d'office aux Edge Functions tant que les clés API héritées (« legacy ») du projet restent actives.
3. `pnpm exec supabase config push` : envoie la configuration Auth de `supabase/config.toml` (connexions anonymes activées, mot de passe de 8 caractères minimum). Attention, elle envoie aussi les réglages de développement : `site_url` en `localhost` et emails non confirmés. Très bien pour un projet de test, à revoir avant la production.
4. Dans le tableau de bord, Authentication → Sign In / Providers : vérifier que « Allow anonymous sign-ins » est activé. Sans cette option, un téléphone enfant ne peut pas être appairé.
5. Dans `apps/mobile/.env.local` : `EXPO_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co` et `EXPO_PUBLIC_SUPABASE_KEY=` la clé publishable (Project Settings → API Keys, `sb_publishable_…`). Jamais la clé secrète ni `service_role`. Relancer `pnpm mobile`, car les variables `EXPO_PUBLIC_` sont figées au démarrage de Metro. Une URL en ligne n'est jamais réécrite par `dev-host.ts`.

Les types TypeScript restent générés depuis la base locale (`pnpm supabase:types`) : appliquer les mêmes migrations aux deux bases.

**Notifications sur téléphone** : il faut un projet EAS. Lancer une fois `npx eas-cli init` dans `apps/mobile` (gratuit, aucun build ; demande un compte Expo) : il écrit `extra.eas.projectId` dans `app.json`, à commiter. Sur iPhone, Expo Go reçoit alors les notifications. Sur Android, Expo Go ne reçoit plus de notifications à distance depuis le SDK 53 : l'app y tourne sans push (le parent voit « ne peut pas recevoir de notifications »), et il faut un build de développement (`eas build`, qui consomme des crédits : demander avant) pour les tester. Avec Supabase local, les rappels partent du conteneur Docker de la base, qui doit pouvoir joindre `exp.host`. Pour suivre les envois : `select kind, title, body, sent_at, push_status, push_errors from notifications order by created_at desc;` dans Studio.
